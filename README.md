# Контроль ремонта квартиры

Django-приложение с регистрацией по email, проектами, командой, этапами ремонта и историей действий. Интерфейс находится в `apps/workspace/` и использует оформление из предоставленного UI-макета.

Регистрация подтверждается шестизначным кодом из письма. Отправка через Gmail настраивается в `.env`: [подключение почты и проверка трёх обычных аккаунтов](docs/EMAIL_SETUP.md).

Матрица прав и границы текущей реализации: [docs/ROLE_ACCESS.md](docs/ROLE_ACCESS.md).

Добавлен этап **40% по ТЗ**: задачи со сроками и назначением исполнителя, фотоотчёты, прогресс по принятым этапам, приёмка и замечания. Сценарий трёх ролей, демонстрационные данные и новые API: [docs/MILESTONE_40.md](docs/MILESTONE_40.md).

## Работа внутри проекта

1. Откройте **Мои проекты → Создать проект**. Обязательно название; адрес квартиры и описание можно заполнить позже.
2. Откроется страница проекта. Заказчик видит контроль команды и плана, прораб — подготовку этапов и недостающие назначения, исполнитель — информацию о ремонте. Заказчик может изменить реквизиты через **Настройки проекта**.
3. Во вкладке **Команда** выберите ранее добавленного человека или введите email. Заполняется один из двух вариантов. По умолчанию назначается роль исполнителя.
4. Исполнитель с активным подтверждённым аккаунтом добавляется сразу. Прораб всегда получает приглашение и доступ только после принятия. Приглашение отображается в его кабинете. Для нового или ещё не подтверждённого email создаётся приглашение. Передайте ссылку человеку; после регистрации и подтверждения почты он должен открыть её и принять приглашение. Автоматической отправки приглашений по email пока нет.
5. Контакт сохраняется в личном списке заказчика. Его можно выбрать в следующем проекте, даже после удаления человека из прежней команды. Списки контактов других пользователей недоступны. Существующие участники и приглашения переносятся в контакты миграцией.
6. На странице проекта впишите название этапа и нажмите **Добавить этап**. Этап получает следующий номер. Даты и ответственный на стадии планирования необязательны.
7. Через **Настроить этап** добавьте описание, сроки и ответственного из команды. Редактирование плана не запускает ремонт. По ТЗ запуск выполняет заказчик после принятия приглашения прорабом и утверждения сметы; этот отдельный процесс пока не реализован. Даты окончания раньше начала отклоняются.
8. Кнопки ↑ и ↓ меняют порядок работ. Во вкладке **Этапы ремонта** также есть поиск и фильтр по статусу. Изменения фиксируются во вкладке **История**.

Заказчик управляет проектом и командой; заказчик и прораб управляют этапами. Исполнители просматривают только свои проекты. В проекте один заказчик и не больше одного прораба, включая ожидающее приглашение прорабу. Чтобы убрать участника или изменить его роль, сначала переназначьте его этапы. Удалить можно собственный запланированный этап без зависимых записей. Назначение существующего исполнителя прорабом требует удаления из исполнителей и нового приглашения с ролью прораба.

## Запуск в PowerShell

Из корня проекта:

```powershell
.\venv\Scripts\python.exe -m pip install -r requirements.txt
.\venv\Scripts\python.exe manage.py migrate
.\venv\Scripts\python.exe manage.py runserver 127.0.0.1:8000
```

Если окружения нет: `py -m venv venv`. Откройте http://127.0.0.1:8000/projects/.

Для проверки используйте обычную регистрацию и три аккаунта, которым назначаются роли в проекте. Подтверждение почты выполняется шестизначным кодом через настроенный Gmail SMTP; автоматического подтверждения и вывода кодов в терминал нет. Старые команды `seed_demo` и `seed_milestone40` остаются необязательными и сами не запускаются.

Для ngrok оставьте сервер работающим, а в другом терминале выполните `ngrok http 8000`. Домен туннеля добавьте в `ALLOWED_HOSTS` без протокола и завершающего слеша, а origin с `https://` — в `CSRF_TRUSTED_ORIGINS`.

## API для команды

Аутентификация — Django session; изменяющие запросы требуют CSRF. Вход: `/accounts/login/` или `/api/auth/login/` для browsable API. Swagger пока не подключён.

| Метод и адрес | Назначение |
|---|---|
| `GET /api/projects/` | Доступные пользователю проекты |
| `POST /api/projects/` | Создать проект: name, необязательные address и description |
| `GET /api/projects/{id}/` | Реквизиты проекта |
| `PATCH /api/projects/{id}/` | Изменить реквизиты, только заказчик |
| `GET /api/contacts/` | Личный список ранее добавленных людей |
| `GET /api/projects/{id}/members/` | Команда с ID участника, именем, email и ролью |
| `POST /api/projects/{id}/members/` | Добавить по email или contact_id; role по умолчанию executor |
| `PATCH /api/projects/{id}/members/{member_id}/` | Изменить role |
| `DELETE /api/projects/{id}/members/{member_id}/` | Удалить из команды, сохранив контакт |
| `GET, POST /api/projects/{id}/invitations/` | Просмотр и создание явных приглашений: email, role |
| `POST /api/projects/{id}/invitations/{invitation_id}/cancel/` | Отменить приглашение |
| `POST /api/invitations/{token}/accept/` | Принять приглашение своим аккаунтом |
| `GET /api/projects/{id}/events/` | История для заказчика и прораба |
| `GET, POST /api/projects/{id}/stages/` | Этапы конкретного проекта / создание этапа |
| `GET, PATCH, DELETE /api/stages/{stage_id}/` | Просмотр, изменение, удаление этапа с проверкой доступа |

Добавление участника: `{"email": "worker@example.com", "role": "executor"}` либо `{"contact_id": 12, "role": "executor"}`. Ответ 201 содержит `{"kind": "member", "member": {...}}` или `{"kind": "invitation", "invitation": {...}}`. Список приглашений проекта видит только заказчик, а получатель видит свои входящие приглашения; приглашение одноразовое и действует 7 дней. Старый endpoint явных приглашений сохраняет сценарий с обязательным принятием.

Минимальный этап: `{"name": "Демонтаж"}`. Дополнительно: `description`, `start_date`, `end_date`, `responsible`, `position`. Если position пропущен, этап добавляется в конец. `responsible` — **ID ProjectMember, не пользователя**. Для запланированного этапа даты и ответственный могут быть null. Через этот API можно планировать этапы, но нельзя запускать работы или подменять приёмку изменением status.

Целевой цикл по ТЗ: `planned → in_progress → pending_acceptance → accepted`. Передача на приёмку принадлежит прорабу, приёмка — заказчику и выполняется отдельным действием. Запуск и согласование сметы пока не реализованы: смена status через обычное редактирование запрещена. Ранее сохранённые статусы, в том числе completed, оставлены в базе без преобразования.

## Структура

- `apps/accounts/`: пользователь `accounts.User`, регистрация, подтверждение email, вход, восстановление пароля.
- `apps/projects/`: Project, ProjectMember, SavedContact, ProjectInvitation, ProjectEvent; проверки ролей и сервисы управления командой.
- `apps/repairs/`: Stage и сервисы создания, изменения, перемещения и удаления этапов.
- `apps/workspace/`: Django-формы, страницы и статические файлы интерфейса. `/projects/{id}/` — обзор проекта, вложенные `/members/`, `/stages/`, `/history/` — его разделы.

Изменения выполняйте через `services.py`: там общие для API и интерфейса права, транзакции, проверки и журнал. Новые модули связывайте с Project и Stage; важные зависимые записи защищайте через `on_delete=PROTECT`. Пользователя всегда берите через `settings.AUTH_USER_MODEL` или `get_user_model()`.

Эта реализация хранит название, адрес и описание проекта. Добавлены задачи, фотоотчёты к задачам и приёмка с замечаниями. Площадь, бюджет, фотографии самого объекта, сметы, архивирование и полный жизненный цикл проекта пока не реализованы. Существующие данные сохраняются при обычном `migrate`.

SQLite не поддерживает блокировку строк через SELECT FOR UPDATE. Для конкурентной работы общего сервера используйте БД с поддержкой таких блокировок, например PostgreSQL. Уникальность участников, прораба и контактов дополнительно защищена ограничениями БД.

Если база создана до перехода на `accounts.User`, не удаляйте её: сначала сохраните копию и отдельно перенесите пользователей и внешние ключи. Ранее обнаруженная пустая локальная база сохранена в `db.sqlite3.before-email-user.*.bak`.

## Проверки

```powershell
.\venv\Scripts\python.exe manage.py check
.\venv\Scripts\python.exe manage.py makemigrations --check --dry-run
.\venv\Scripts\python.exe manage.py test apps.accounts apps.projects apps.repairs apps.workspace
```

Тесты проверяют регистрацию и вход, роли и изоляцию проектов, контакты и повторное добавление, приглашения, работу страниц, CSRF, разделение кабинетов и прав, планирование без назначения, защиту от обхода запуска и приёмки через status, порядок этапов.
