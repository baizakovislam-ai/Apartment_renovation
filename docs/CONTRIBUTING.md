# Как заливать работу в GitHub

Правило одно: **одна функция — одна ветка — один PR.** Так тимлид видит, кто и что сделал, и может проверить каждую функцию отдельно.

## 1. Ветка

Ветка создаётся от свежего `main`:

```powershell
git switch main
git pull
git switch -c islam/notifications
```

Название: `<имя>/<что-делаем>`, латиницей, через дефис.

| Что | Пример |
|---|---|
| Новая функция из ТЗ | `islam/notifications`, `abdulazis/pdf-report`, `bekzat/project-finish` |
| Исправление ошибки | `islam/fix-estimate-revision` |
| Только документация | `islam/docs-demo-estimate` |

Нельзя:
* коммитить прямо в `main`;
* складывать несколько функций в одну ветку («Сделано 40%»);
* делать `git push --force` в `main` и в чужие ветки.

## 2. Коммиты

Первая строка — что изменилось, по-русски, до ~70 символов. Ниже, если нужно, — зачем.

```
Уведомления: письмо о просроченной задаче

Раз в сутки исполнителю и прорабу уходит письмо со списком
просроченных задач (FR19).
```

Плохо: `fix`, `20%`, `обновил`, `почти готово`.

Перед коммитом проверьте `git status`: в коммит не должны попасть `.env`, `db.sqlite3`, `media/`, `venv/`.

## 3. Перед PR

```powershell
git fetch origin
git merge origin/main          # подтянуть чужие изменения и решить конфликты у себя
.\venv\Scripts\python.exe manage.py test
git push -u origin islam/notifications
```

## 4. Pull Request

* Открыть PR из своей ветки в `main`. Описание подставится из шаблона `.github/pull_request_template.md` — заполните все разделы, особенно «Как проверить».
* Название PR — как первая строка коммита: `FR19 Уведомления по срокам и просрочкам`.
* Один PR — до нескольких сотен строк. Если функция большая, делите на шаги: модели и логика → API → страницы.
* Сливает PR тимлид (или другой участник после проверки), не автор.
* После слияния ветку можно удалить на GitHub.

## 5. Если в PR нашли ошибку

Исправьте в той же ветке и сделайте `git push` — PR обновится сам. Новый PR открывать не нужно.

## Кто за что отвечает
