# Часть Абдулазиса: что входит, как проверить, где код

По таблице распределения работ в ТЗ за Абдулазисом закреплены:

| Этап | Функции |
|---|---|
| 20% | Авторизация и регистрация (FR01) |
| 40% | Фотоотчёты (FR06), прогресс ремонта (FR08) |
| **60%** | **Изменение сметы (FR11): гибкое управление бюджетом — добавление или удаление товаров и услуг** |
| **80%** | **Прайс-лист прораба (FR14)** |
| **100%** | **Итоговый отчёт и экспорт в PDF (FR21)** |

Этот документ описывает часть **60% — FR11 «Изменение сметы»**, часть **80% — FR14 «Прайс-лист прораба»** и часть **100% — FR21 «Итоговый отчёт»** (две последние — в конце документа).

## Что требует ТЗ

> **FR11.** Система должна поддерживать изменение утверждённой сметы. Для изменения указываются: причина; изменяемая позиция; новое значение; изменение стоимости; изменение сроков.

Связанные требования, которые тоже выполнены:

| Требование ТЗ | Как выполнено |
|---|---|
| 4.1.1: прораб «предлагает изменения», заказчик «утверждает изменения сметы», прораб не утверждает собственные заявки | Заявку составляют прораб или заказчик, одобряет или отклоняет только заказчик |
| 4.1.1, прил. А: исполнитель не имеет доступа к смете | У исполнителя нет пункта меню, страницы и API отдают 403 |
| Прил. Б: статусы заявки «Черновик → На согласовании → Одобрена / Отклонена / Отозвана» | Ровно эти пять статусов (`ChangeRequest.Status`) |
| Прил. В: сущность «Заявка на изменение» | Модели `ChangeRequest` (заявка) и `ChangeItem` (изменяемая позиция) |
| 4.12: для согласованных данных — история версий; безвозвратно удаляются только собственные черновики | Утверждённая смета не правится: при одобрении создаётся **новая версия**, старая получает статус «Заменена новой версией». Удалить можно только свой черновик заявки, отправленную — только отозвать |
| 4.12: финансовые операции хранят автора и время решения | `created_by`, `submitted_by/at`, `decided_by/at`, `decision_reason` |
| 4.13: атомарность согласований и финансовых изменений, повторное нажатие не выполняет операцию дважды, конфликт версий — сообщение без потери чужих данных | Одобрение — одна транзакция с блокировкой строк. Повторное «Одобрить» получает «Решение уже принято». Счётчик `revision` защищает от правки в двух вкладках. Кнопки в формах блокируются после первого нажатия (`data-once`) |
| FR13: остаток бюджета | В заявке видно: смета до и после, лимит бюджета, остаток до и после, превышение лимита |
| FR17: поиск и фильтрация согласований | Заявки попадают в журнал «Согласования» (тип «Изменение сметы»), есть вкладки по статусам |
| FR20: история изменений | Каждое действие пишется в «Историю изменений» проекта |

## Как это устроено

```
Утверждённая смета v1 ──► Заявка №1 (черновик)
                            причина: «Подорожал кабель»
                            позиции: изменить / удалить / добавить
                            срок этапа: 10.11 → 14.11
                         ──► На согласовании ──► заказчик: Одобрить ──► смета v2 (утверждена), v1 «Заменена»
                                                                         срок этапа сдвинут
                                            └──► заказчик: Отклонить (причина обязательна)
                                            └──► автор: Отозвать
```

Для каждой позиции заявки хранится **новое значение** (этап, наименование, вид затрат, единица, количество, цена). **Старое значение** берётся из строки утверждённой сметы — она уже не меняется. **Изменение стоимости** считается само: «стало − было» по каждой позиции и в сумме. **Изменение сроков** — необязательный новый срок окончания одного этапа; показывается и разница в днях.

Если смету уже изменили другой заявкой, старую заявку применить нельзя: система предупреждает, что заявка составлена к прежней версии.

### 1. Прораб предлагает изменение

1. Войти как **прораб**. Меню «Деньги и согласования» → «Изменения сметы» (или кнопка «Предложить изменение» на странице утверждённой сметы).
2. Раскрыть «Новая заявка на изменение», написать **причину**. Если меняется срок, выбрать этап и новый срок окончания. «Создать заявку».
3. В таблице «Смета после изменения» у каждой строки утверждённой сметы есть кнопки:
   * ✎ — **изменить позицию**: открыть форму, поменять количество, цену, наименование, этап. Строка подсветится синим, под названием видно «Цена: 900 → 1100».
   * 🗑 — **убрать позицию** из сметы. Строка подсветится красным и будет зачёркнута.
   * ✕ — отменить изменение позиции (оставить как в смете).
4. Внизу форма «Добавить новую позицию» — **новая работа или материал**. Строка подсветится зелёным.
5. Сверху карточки: «Смета сейчас», «Изменение стоимости» (+/−), «Смета после изменения» с остатком лимита, «Изменение сроков» в днях. Справа — влияние на бюджет.
6. «Отправить на согласование». Пустую заявку (без позиций и без нового срока) отправить нельзя.

### 2. Заказчик решает

1. Войти как **заказчик**. На «Главной» в блоке «Требует вашего внимания»: «Изменение сметы №1 ждёт вашего решения».
2. На странице заявки плашка «Одобрить изменение сметы на +… сом?» с кнопками «Одобрить» и «Отклонить…» (причина обязательна).
3. После одобрения: на странице «Смета» — новая утверждённая версия с подписью «Эта версия создана по заявке на изменение №1», старая версия — «Заменена новой версией». Срок этапа на странице «Этапы ремонта» сдвинут.
4. В «Согласованиях» заявка видна с типом «Изменение сметы», суммой изменения и решением. В «Истории изменений» — все шаги.

### 3. Что должно запрещаться

* Создать заявку без утверждённой сметы или без причины.
* «Изменить» позицию на те же значения; количество 0 или меньше; отрицательная цена; пустое наименование.
* Позиция из чужого проекта или из другой версии сметы; этап чужого проекта.
* Новый срок раньше начала этапа или равный текущему; срок принятого или отменённого этапа.
* Менять заявку не в статусе «Черновик»; менять, отправлять, удалять или отзывать чужую заявку.
* Одобрить или отклонить — прорабу и исполнителю. Отклонить без причины.
* Одобрить заявку, если смета уже изменилась после её составления, или пока готовится новая версия сметы (черновик или на согласовании).
* Повторно одобрить уже решённую заявку (двойное нажатие).
* Правка из второй вкладки: «Заявку уже изменил другой пользователь».
* Исполнитель: нет пункта меню, страницы отдают 403, API — 403; посторонний пользователь — 404.


# Часть 80% — FR14 «Прайс-лист прораба»

## Что требует ТЗ

> **FR14.** Прораб может: добавлять работы в свой прайслист; редактировать позиции; удалять позиции. Позиция содержит: название работы; категорию; единицу измерения; цену.

> **UC-22.** Система проверяет обязательные поля и положительное значение цены. Прораб может просматривать, изменять и удалять собственные позиции. Система сохраняет актуальную цену для соответствующей работы и единицы измерения. Результат: прайс-лист обновлён; ранее сохранённые расчёты и утверждённые сметы не изменяются.

| Требование | Как выполнено |
|---|---|
| Добавить, изменить, удалить работу | Страница «Мой прайс-лист», API `/api/price-list/` |
| Позиция: название, категория, единица, цена | Модель `PriceItem`; категории: демонтаж, электрика, сантехника, стены и потолки, полы, плитка, покраска и обои, окна и двери, прочее |
| Обязательные поля, цена больше нуля | Проверки в `apps/pricing/services.py` `clean` + ограничение в базе `price_item_price_positive` |
| Одна актуальная цена для работы и единицы | Вторую «Укладку ламината» за м² добавить нельзя (регистр букв не важен) — система предлагает изменить цену у существующей. За другую единицу (например, м.п.) — можно. Есть и ограничение в базе |
| Прораб меняет только свои позиции | Чужие позиции не видны (404), сервис отвечает 403 |
| Сохранённые расчёты и сметы не меняются | В расчёт цена **копируется**. Изменение или удаление позиции прайс-листа не трогает расчёты и сметы |
| Исполнитель не видит цен (4.1.1, прил. А) | Нет пункта меню, страница и API — 403 |
| Связь с FR16 / UC-23 «источник цены: прайс конкретного прораба» | В предварительном расчёте блок «Из прайс-листа прораба»: выбрать работу, указать объём — цена и единица подставятся |

Кто ведёт прайс-лист: пользователь, который является прорабом хотя бы в одном проекте (роль в системе задаётся участием в проекте). Прайс-лист личный — один на прораба, общий для всех его проектов. Заказчик видит прайс-лист прораба своего проекта только для чтения.

## Как проверить (демо)

На существующей базе после обновления кода:

```powershell
.\venv\Scripts\python.exe manage.py migrate
.\venv\Scripts\python.exe manage.py seed_pricelist
```

На новой базе `seed_demo` сразу заполняет прайс-лист демо-прораба (15 работ).

### 1. Прораб ведёт прайс-лист

1. Войти как **прораб** (`foreman@example.com`). В меню «Рабочее пространство» → **«Мой прайс-лист»**.
2. Вверху вкладки по категориям с количеством, строка поиска по названию.
3. Внизу «Добавить работу»: название, категория, единица (подсказки м², шт, м…), цена. «Добавить».
4. ✎ у позиции — изменить (например, цену). 🗑 — удалить (с подтверждением).

### 2. Заказчик и предварительный расчёт

1. Войти как **заказчик**. Открыть проект → «Деньги и согласования» → **«Прайс-лист прораба»**: список цен прораба, без кнопок изменения.
2. «Предварительный расчёт» → открыть расчёт. Блок **«Из прайс-листа прораба»**: выбрать работу, ввести объём, «Добавить». Строка появится в расчёте с ценой из прайс-листа.
3. Войти прорабом, поменять цену этой работы. Вернуться в расчёт — цена в нём **не изменилась**.

### 3. Что должно запрещаться

* Пустое название или единица; не выбрана категория; цена 0, отрицательная или не число.
* Вторая позиция с тем же названием и той же единицей.
* Менять или удалять чужие позиции (404 на странице и в API).
* Вести прайс-лист заказчику или исполнителю: страница «Мой прайс-лист» объясняет, что его ведёт прораб, API — 403.
* Добавить в расчёт работу из прайс-листа прораба другого проекта; объём 0 или меньше.
* Исполнитель: нет пункта меню, страница и API прайс-листа проекта — 403.

# Часть 100% — FR21 «Итоговый отчёт»

## Что требует ТЗ

> **FR21.** Заказчик и прораб могут сформировать итоговый отчёт по проекту. Отчёт содержит: информацию о проекте; этапы; сроки; смету; расходы; выполненные работы; замечания; итоговую стоимость ремонта.

> **UC «Формирование итогового PDF-отчёта».** Система собирает сведения о проекте, этапах, сроках, смете, подтверждённых расходах, выполненных работах и замечаниях, формирует итоговую фактическую стоимость ремонта, создаёт PDF-документ; пользователь его скачивает. PDF содержит сведения в пределах прав пользователя.

| Раздел отчёта | Что в нём |
|---|---|
| 1. Информация о проекте | Адрес, площадь, статус, заказчик, прораб, исполнители, лимит бюджета, готовность в %, описание |
| 2. Этапы и сроки | Плановые сроки проекта, фактическое окончание (когда приняты все этапы) и отклонение в днях, число этапов с нарушением срока. Таблица этапов: статус, ответственный, план, дата приёмки, просрочка в днях, готовность |
| 3. Смета | Утверждённая версия: все позиции по этапам с итогами, первоначальная стоимость, одобренные заявки на изменение (№, причина, кто и когда одобрил, изменение суммы) |
| 4. Расходы | См. ниже |
| 5. Выполненные работы | Принятые этапы, выполненные задачи (исполнитель, дата, результат), количество фотоотчётов |
| 6. Замечания | Все замечания (кроме снятых): этап, ответственный, статус, дата закрытия |
| 7. Итоговая стоимость | Сумма, откуда она взята, лимит бюджета и остаток или превышение |

Права (прил. А «Формирование PDF-отчёта»: заказчик — да, прораб — да, исполнитель — нет): у исполнителя нет пункта меню, страница, PDF и API — 403; посторонний пользователь — 404.

**Про расходы.** Учёт расходов (FR12) сделан в части Бекзата на 60%. Функция `confirmed_expenses` в `apps/reports/services.py` возвращает подтверждённые заказчиком расходы: отчёт показывает их таблицей (дата, расход, категория, сумма), и итоговая стоимость считается **по подтверждённым расходам**. Черновики, ожидающие и отклонённые расходы в отчёт не входят. Пока подтверждённых расходов нет, итоговая стоимость берётся по утверждённой смете с учётом одобренных изменений.

## Как проверить (демо)

После обновления кода установите зависимости (добавлен `reportlab` — библиотека для PDF). `start.bat` делает это сам, вручную:

```powershell
.\venv\Scripts\python.exe -m pip install -r requirements.txt
```

1. Войти как **заказчик** или **прораб**, открыть проект → «Деньги и согласования» → **«Итоговый отчёт»**.
2. На странице: итоговая стоимость, остаток лимита, готовность, замечания и все разделы отчёта.
3. Кнопка **«Скачать PDF»** — скачается файл `report-project-1-ГГГГ-ММ-ДД.pdf` (A4, русские буквы, номера страниц, внизу — кто и когда сформировал).
4. Войти **исполнителем** — пункта «Итоговый отчёт» нет, прямая ссылка даёт 403.
