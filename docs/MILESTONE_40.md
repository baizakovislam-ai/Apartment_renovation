# Этап 40 процентов

Объём взят из строки «40% — 15 ноября 2026 года» таблицы распределения работ в ТЗ. Реализованы задачи и сроки, фотоотчёты, прогресс, приёмка этапов и замечания. Регистрация, вход, восстановление пароля, существующие проекты, приглашения и оформление сохранены. Новые разделы находятся во вкладках открытого проекта.

## Сценарий работы

1. Заказчик или прораб создаёт задачу: название, этап, описание, исполнитель и срок. Исполнитель выбирается из команды текущего проекта. Срок задачи должен попадать в заданные сроки этапа. Для ещё не запущенных этапов доступно планирование.
2. Исполнитель видит только свои задачи. Для работающего этапа он нажимает «Начать выполнение», добавляет текст результата или фотоотчёт, затем передаёт задачу на проверку.
3. Заказчик или прораб подтверждает выполнение либо возвращает задачу с причиной. Возврат и результат видны в истории задачи. Собственный черновик задачи можно удалить, если нет отчётов. Изменение реквизитов и переназначение доступны до начала выполнения.
4. Фотоотчёт содержит описание, автора, время и 1–8 фотографий JPEG, PNG или WebP, до 8 МБ и 25 Мп каждая. Фотографии проверяются по содержимому, повторно кодируются без исходных метаданных и выдаются через проверку доступа к задаче. Публичную раздачу каталога `media/private/` подключать нельзя.
5. Прораб передаёт этап на приёмку после выполнения и проверки всех его задач и закрытия замечаний. Заказчик принимает этап либо возвращает с причиной. Решение, автор и время сохраняются.
6. Заказчик создаёт замечание с описанием, ответственным и сроком. Замечание к этапу на приёмке возвращает его в работу. Исполнитель или прораб отвечает и сообщает об устранении; только заказчик подтверждает устранение и закрывает замечание либо возвращает его на доработку. Состояние «Устранено» ещё блокирует приёмку.
7. Прогресс — доля принятых заказчиком этапов среди всех неотменённых этапов. Отдельно показываются выполненные и просроченные задачи. Этап «На приёмке» ещё не считается принятым.

Изменения задач, фотоотчётов, замечаний и приёмки фиксируются в общей истории проекта. Счётчик `version` защищает задачи и замечания от перезаписи устаревшей формой. `acceptance_version` защищает решения о приёмке. UUID `request_id` предотвращает повторное создание при повторной отправке формы; для такой же защиты API-клиент должен повторно передавать тот же UUID.

## Граница со следующим этапом

По ТЗ запуск работ выполняет заказчик после принятого приглашения прораба и утверждения сметы. Смета относится к этапу 60%, поэтому кнопка обхода этого условия не добавлена. В настоящем новом проекте можно составлять план; выполнение задач и приёмка работают для этапов со статусом `in_progress` или ранее сохранённым `completed`. Старые статусы и данные автоматически не переводятся. Финансы, согласование сметы, прайслисты, итоговый PDF, автоматические уведомления и завершение проекта остаются вне этого этапа.

Для демонстрации полного сценария имеется отдельная команда с готовыми учебными состояниями. Она создаёт только новые данные и отказывается работать, если демонстрационные аккаунты уже существуют:

```powershell
.\venv\Scripts\python.exe manage.py migrate
.\venv\Scripts\python.exe manage.py seed_milestone40
```

Команда запросит пароль минимум из 10 символов. Аккаунты: `customer40@example.com`, `foreman40@example.com`, `executor40@example.com`. Это учебный набор уже начатого ремонта, а не механизм запуска настоящего проекта.

Проверка трёх ролей:

1. Исполнитель: в «Электромонтаже» открыть задачу в работе, добавить фотоотчёт и передать на проверку; в «Замечаниях» сообщить об устранении.
2. Прораб: проверить результат задачи; в «Приёмке» передать «Штукатурные работы» заказчику.
3. Заказчик: принять «Штукатурные работы», проверить изменение прогресса; закрыть устранённое замечание либо вернуть с причиной.

## API для команды

Сохраняется существующая аутентификация Django session с CSRF. Все адреса ниже начинаются с `/api/`.

| Метод и адрес | Назначение |
|---|---|
| `GET, POST projects/{id}/tasks/` | Доступные задачи / создание |
| `GET, PATCH, DELETE tasks/{id}/` | Просмотр / изменение своего проекта / удаление собственного черновика |
| `POST tasks/{id}/action/` | `action`: `start`, `submit`, `approve`, `return`; обязательный `version`, необязательный `result` |
| `GET, POST tasks/{id}/reports/` | Отчёты; загрузка multipart с `description`, `images`, необязательным `request_id` |
| `GET, POST projects/{id}/remarks/` | Замечания / создание заказчиком |
| `POST projects/{id}/remarks/{remark_id}/action/` | `action`: `reply`, `fix`, `close`, `reopen`; `version`, `text` |
| `POST stages/{id}/acceptance/` | `action`: `submit`, `accept`, `return`; `version` из `acceptance_version`, `reason` |
| `GET projects/{id}/progress/` | Прогресс проекта |

Создание задачи: `name`, `stage` (ID этапа), `assignee` (ID участия ProjectMember с ролью executor), `due_date` в формате `YYYY-MM-DD`; необязательные `description`, `request_id`. Изменение и удаление требуют текущий `version` в теле запроса. Обычный PATCH не меняет статус. Создание замечания: `stage`, `description`, `responsible` (ID участия), `due_date`, необязательный `request_id`.

Прямые адреса фотографий возвращаются как `/private/photos/{id}/`; они требуют авторизацию и доступ к задаче. Сырые пути хранилища не возвращаются.

Добавление фотоотчёта также увеличивает `version` задачи: перед подтверждением выполнения необходимо просмотреть свежие данные, включая новые фотографии.

## Проверки

```powershell
.\venv\Scripts\python.exe manage.py check
.\venv\Scripts\python.exe manage.py test --noinput
.\venv\Scripts\python.exe manage.py makemigrations --check --dry-run
```

Покрыты роли, изоляция проектов и назначенных задач, сроки, конфликты версий, повторная отправка, корректные и поддельные фотографии, защита файлов, зависимые записи, цикл доработки и блокировка приёмки. Тесты используют отдельную временную БД и временное хранилище фотографий. Для нескольких параллельных пользователей общий сервер следует запускать с PostgreSQL: SQLite не предоставляет блокировку строк `SELECT FOR UPDATE`.
